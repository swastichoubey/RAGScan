# Implementation Report

## V0.1 - Engine Scaffold | 03.09.2026

File Implemented -> Purpose

schema.py -> defines the shape of the data that flows through the engine. Enum for Severity and Vulnerability Class (VulnClass), and Finding references both Severity and VulnClass as typed fields and is a model that records id, vuln_class, severity, a description, location and timestamp. Also defines ScanReport which contains the following scan_id (automatically generated UUID when build_report() is called), target (the artifact that was scanned. Defined as Optional), findings (list of findings for a single specific report), vectordb_name and vectordb_version (both Optional, recorded for audit trail purposes. Addition of these fields was inspired by a ChromaDB incident you can read about here: https://swastichoubey.github.io/public/articles/chromadb-score-discrepancy.html), engine_version (also Optional , useful for reproducibility), generated_at (datetime to record when the report was generated).

base.py -> defines BaseDetector, which is an ABC that both stub detectors implement. It is also the contract through which the Scanner delegates without knowing which concrete detector it is talking to. 
*Note: it is vital that BaseDetector is an ABC otherwise a normal class will allow anyone to add a new detector without vital methods like analyze_chunk(). An ABC (Abstract Base Class) catches the mistake instantly instead of at runtime.*

prompt_injection.py -> currently a stub that just proves that the pipeline works. It checks for a small hardcoded list of obvious phrases, and if found, construct a real Finding with the right vuln_class and severity.

pii_leakage.py -> also a stub that uses regex to look for phone number and email.

aggregator.py -> collects Findings into a list as they come and packages them into a ScanReport.

scanner.py -> Contains Scanner which our interface (web/CLI) will actually import.

test_scanner_smoke.py -> defines the minimal check to ensure that the pipeline works.


### Limitations and Considerations

1. Consideration (schema.py -> Finding) => Finding.timestamp currently uses default_factory (auto-populated). Alternative considered: require it explicitly at every call site, as a forcing function to stay deliberate about when detection actually happened. Revisit after V0.1 is exercised more.
2. Consideration (schema.py -> ScanReport) => Currently the scan_id is a UUID being generated automatically, consider letting it be generated by whatever calls build_report(). Using the latter allows for consistency between Finding.id and ScanReport.scan_id.
3. Limitations (pii_leakage.py) => currently only considers email and phone number as PII. Actual information considered as PII is an exhaustive list so it should be expanded to include Government ID, Medical Records, Biometric Data, Financial Records, Demographic, Digital Identifiers, etc. Also, a real number like +1-989-763-5402 written with hyphens throughout would currently still match correctly, but something like 19897635402 (no separator between country code and number) would misfire.
